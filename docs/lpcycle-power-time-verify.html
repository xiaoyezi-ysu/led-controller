0. 结论先说

① 低功耗指令有效且稳定。睡态实测 0.226 mA（六组独立采集一致落在 0.220–0.229 mA），4G 已断电、会话结束自动再睡；每轮「睡 ↔ 会话 ~90.6 s」精确复现，多轮零人工干预。折算到 2 h 上报间隔，整机平均电流 0.77 mA，已在 1 mA 以内。
② 校时链路已打通。每轮会话收尾用 DTU 的 config,get,nettime 对表 —— 第 2 轮结尾首次成功，第 3、4 轮实测 RTC 与 PC 墙钟误差稳定在 1–2 s、浸泡后复查更读到 0 s（此前 RTC 只数「开机秒数」，第 1、2 轮读数 58→215 即为佐证）。
③ 但顺带挖出并修复了一个把会话掐断的真 bug。首轮实测会话只有 13.7 s（代码设定 90 s），根因是 uint32 下溢（下行 §4）。它连锁导致 4G 来不及注网、报告发不出、nettime 授时必然失败 —— 修完三项一起恢复正常。
④ 两个预设被实验修正：（a）历史上记的睡态 1.0 mA「是 DBG_STOP 保活调试域所致」——已用对照实验否证，两组只差 1 µA（§2）；（b）更重要的是，之前那个 2.3 mA 档根本不是 Stop 而是 Sleep，本次分层实测把 3.47→0.226 mA 的账拆清了（§1）；（c）测试期间那次非预期复位（PORRSTF+PINRSTF）——10 分钟纯净浸泡后 RCC_CSR=0x00000000、零复位，判为测试台架噪声，产品路径无风险（§6）。

1. 为什么能从 2.3 mA 降到 0.226 mA —— Run / Sleep / Stop 分层实测

结论先给：降下来的功劳不是 4G 模组，而是 MCU 从「Sleep」换成了「真 Stop」。 此前记录的 2.31 mA 那一档，其实根本没进 Stop，只进了 Sleep（Cortex-M3 的 Sleep 只停内核时钟，外设时钟和振荡器照跑）。 4G 模组在三个测量点上都是 V4G_Set(0) 断主电的状态，不参与这 2 mA 的差别。

为什么 Stop 能一口气省 2 mA？

模式时钟树典型电流（F103 @8 MHz）
RunHSE 8 MHz + PLL off，AHB/APB 全开~2.4 mA
Sleep（SLEEPDEEP=0）内核时钟停，但 HSE 振荡器和 AHB/APB 总线照常跑——外设寄存器随时可读~2.2 mA
Stop（SLEEPDEEP=1）整个时钟树停振（HSE 关、HSI 关），只留 LSE 32.768 kHz 给 RTC~0.02 mA（+板上 LDO 静态与漏电 ≈0.2 mA）
直观理解：Sleep 只是「CPU 打个盹」，8 MHz 那套时钟还在全速空转，总线、Flash 接口、外设时钟一个没停 —— 所以电流几乎没降。 Stop 是「把整个时钟系统关掉」，MCU 本体瞬间掉到几十 µA，剩下的 0.2 mA 主要是板上 LDO 静态电流、SC7A20H 漏电和 4G 断电路径的漏电。
所以「整机从 2.3 mA 变 0.22 mA」真正的开关是 SCB_SCR 的 SLEEPDEEP 位：老代码的 g_low_power 路径没置它（因为那个模式依赖 UART 唤醒，进 Stop 就收不到 UART 了，属于设计取舍），lp_cycle 才第一次真正把它置起来。
⚠ 顺带纠正一个历史误判：之前记录的「4G 断 + Stop = 2.31 mA」并不是 Stop，而是 Sleep —— 本次实测 Sleep = 2.22 mA，与 2.31 只差 0.09 mA（可归因于当时 LEDB2 状态或换挡噪声）。 当时用 SWD 手写 SCB_SCR=0x04 想手动进 Stop，但固件主循环每一圈都会重写这个位 （main.c：if (lp_stop) SCR |= SLEEPDEEP; else SCR &= ~SLEEPDEEP;）， 非 lp_cycle 睡眠态下 lp_stop=0 → 手写的 SLEEPDEEP 下一圈就被清掉，于是永远停在 Sleep。

按周期折算的平均电流

先纠正一个口径问题：指令里的 period_min 其实是「睡眠时长」，不是「上报周期」。
证据在 LP_CloseAndSleep()：闹钟是在收尾序列的最末尾才挂的 —— +++ → nettime 对表 → AT+ENTM → RTC_APP_ArmIn(g_lp_period_s) → V4G_Set(0) → Stop。 所以闹钟从「收尾结束的那一刻」起数 period 秒，两次上报的真实间隔 = period + 会话 90.6 s + 收尾 4.1 s ≈ period + 95 s。
实测印证（两条独立证据吻合）：period_min=60 时 —— ① F-11 电流曲线里三个完整循环都是「睡 ~63 s ↔ 醒 ~96 s」、整周期 ≈155 s；② SWD 状态抓取里 state=2→1 的间隔为 60 / 61 / 61 s、state=1→2 为 94 s（§5）。

折算公式（口径 = 固件真实行为）：I_avg = (period × 0.226 mA + 4840 mA·s) / (period + 94.7 s)
其中 4840 mA·s 是实测每轮醒窗的电荷量（96 s 窗 × 50.4 mA），睡态取 0.226 mA。

4. 修复：会话被「瞬间掐断」的 uint32 下溢

症状

修复前实测：唤醒后 13.7 s 就进收尾，而代码里 LP_SESSION_MS = 90000（90 s）。连锁后果：4G 模组启动需要 20–60 s，永远来不及注网 → MQTT 报告发不出、nettime 授时必然拿不到应答 → RTC 只数开机秒数。

根因

__WFI();                                  // Stop 期间 SysTick 被挂起
uint32_t now = HAL_GetTick();             // ← 取到的是「睡眠前的冻结值」

if (g_rtc_alarm_hit) {                    // 被 RTC 闹钟唤醒
    HAL_ResumeTick();
    SystemClock_Config();                 // 这几步耗时几毫秒
    V4G_Set(1);
    s_lp_t0 = HAL_GetTick();              // ← 已比上面的 now 大几毫秒
    s_lp_state = 1;
}
...
if (g_lp_cycle && s_lp_state == 1) {
    uint32_t t_in = now - s_lp_t0;        // ← 负数！uint32 下溢 → 0xFFFFFFxx
    if (t_in >= LP_SESSION_MS)            // 0xFFFFFFxx ≥ 90000 → 立即成立
        s_lp_state = 2;                   // 会话第一圈就被判超时
}
实质：「同一圈里 now 是睡眠中的冻结值，而 s_lp_t0 是几毫秒之后的新值」，两者相减为负，在无符号运算里变成约 42.9 亿 —— 远大于 90000，于是会话在第一圈就被判超时。

修复（两处，均在 Core/Src/main.c）

  1. 唤醒处理块末尾刷新时基：now = HAL_GetTick();（供本圈剩余逻辑：会话计时 / DTU / ACK / SC7 使用）；
  2. 会话推进处直接现读：uint32_t t_in = HAL_GetTick() - s_lp_t0;（不再依赖本圈开头的 now）。

一个容易踩的细节：uwTick 在睡眠期是冻结的

实测：一次 60 s 的睡眠里墙钟走了 65 s，而 uwTick 只涨了 4.7 s —— 因为进 Stop 前调了 HAL_SuspendTick()。 这正是 §4 那个 uint32 下溢 bug 的土壤：任何「唤醒后立刻用 HAL_GetTick() 相减」的代码都要当心本圈取到的 now 还是睡眠前的冻结值。 这也是为什么修复选择了「在唤醒块末尾显式刷新 now」+「会话推进处现读」双保险。

附：DTU 侧 ntptime 已通过 PC 直连设为 1（每小时 NTP 对时并持久化），因此 nettime 读到的是 NTP 校准后的时间，而非纯基站时间。

结论：那是一次台架噪声，不是固件问题。642 s / 4 个完整循环里复位标志全程为 0，说明固件自身的唤醒—会话—收尾—再睡链路稳定；之前的复位只出现在「同时开着探针 + F-11」的采集里。

两个候选来源（均为测试台架相关）

  • F-11 自动换挡继电器：电流在 0.22 mA ↔ 59 mA 之间跳变时，F-11 靠继电器切换量程，切换瞬间可能短时断开被测回路 → 供电跌落 → 掉电复位。会话里记录到的约 1.2 A 开机浪涌也会加剧这一点。
  • 调试器 connect-under-reset：目标在深度 Stop 时 SWD 失联（固件未使能 DBG_STOP），调试器为恢复连接可能拉低 NRST → 引脚复位。
对产品的影响：无。两个来源都需要「外接电流表 + 调试器」才成立。真机上既没有换挡继电器，也没有常驻的调试器。
但仍建议顺手加固：4G 模组上电瞬间的 ~1.2 A 浪涌对供电裕量不友好，建议在模组 VCC 就近放一颗大容量电容（如 470 µF）或加软启动，避免弱供电场景下（如太阳能板阴天）被浪涌拉垮导致掉电复位。

7. 复现与操作备忘

开：MQTT 下发  {"cmd":"lp_cycle","period_min":60}
关：MQTT 下发  {"cmd":"lp_cycle_off"}      （或 SWD 写 g_lp_cycle=0 / s_lp_state=0）

⚠ period_min 是「睡多久」，不是「多久报一次」
   真实上报间隔 = period_min×60 + 90.6 s（会话）+ 4.1 s（收尾）
   想让上报间隔 = T，应下发 period_min ≈ (T − 95 s) / 60

关键 RAM 符号（本轮固件）
  g_lp_period_s = 0x2000000C   （睡眠时长，秒）
  g_lp_cycle    = 0x200004C1
  s_lp_state    = 0x200004C2   （0 idle / 1 session / 2 closing / 3 sleeping）
  s_lp_t0       = 0x200004C4
  uwTick        = 0x20000120
  _4g_state     = 0x200004D0   （14 = READY）

复位原因判读
  RCC_CSR = 0x40021024    bit27 PORRSTF · bit26 PINRSTF · bit28 SFTRSTF · bit29 IWDGRSTF
  清标志：写 bit24 RMVF
测量注意：Stop 期间若未使能 DBGMCU_CR 的 DBG_STOP 位，SWD 会失联（读回 0 字节或全 0）——这是正常现象，也是真实产品功耗的前提。
⚠️ 但注意：本轮的对照实验（§2）显示，使能该位并不会明显抬高睡态电流（两组差 1 µA）。所以「历史上 1.0 mA 是因为开了 DBG_STOP」这个说法不成立，不要再用它解释任何功耗偏差。
⚠️ 另一个坑：不要再用 SWD 手写 SCB_SCR 去手动进 Stop。固件主循环每一圈都会重写这个位（lp_stop 为 0 时清掉），手写的 SLEEPDEEP 活不过一圈 —— 这就是早期「Stop 只有 2.3 mA」的根源（见 §1）。要测 Stop 就让 lp_cycle 自己走。
⚠️ 还有一个实验副作用（已修）：本次分层实验里用 SWD 人工注入 s_lp_state=2 之后，板子卡在 Stop 里没被闹钟唤醒（F-11 实测 0.200 mA 死平数十分钟，SWD 完全读不到）。处置：继电器 power-cycle → 重新下发 lp_cycle(period=60) → 恢复正常。
恢复后复验（208 s）：状态序列 Stop 睡 → 会话 89 s → 收尾 6 s → Stop 睡 59 s → 会话，整周期 155 s；睡态中位 0.211 mA、睡段恰好 58 s —— 与正常流程完全一致。所以「卡住」是人工拼状态的副作用，不是固件的常态行为（642 s 浸泡 / 4 个完整循环里从未出现）。
