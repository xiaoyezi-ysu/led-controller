> 测试日期：2026-10-12 19:47–19:49
> 硬件：车牌板（LICENSE_PLATE_BOARD）+ 银尔达 YED_DTU4 透传模组 + SC7A20H
> 测量：MKLink 探针 `power-read --port COM11`（MCU 下载器 VCC 输出的实际供电，ADC 10 点均值）
> 切状态：MQTT 下行（`xiaoyeziUESTC1147/<ICCID>`），上行 `DTU_Topic1147/#`

## 结论

1. **耗电大头是 4G 模组，不是 MCU / LED。** 所有档位的电流下限都落在 33~36 mA，这是模组维持 MQTT 连接的基础电流（含周期性 TAU / 心跳突发，所以 `max` 常冲到 100~160 mA）。
2. **睡眠态确实有效**：avg 从运行态 ~81 mA 降到 40.33 mA，P_avg 273.5 → 136.0 mW（约 **-50%**）。省下的是 CPU 内核空转 + 1ms SysTick 中断 + STM32 侧心跳/探活发言。
3. **睡眠态仍不够"深"**：模组照常供电、MQTT keepalive 照跑，且模组的 `ready` 心跳 / 回显会不时通过 USART1 把 MCU 从 WFI 唤醒 —— 所以 40 mA 是"MCU 休息、模组值班"的水平，不是整机低功耗。
4. **LED 的电流贡献无法从本组数据里分离**：4G 突发噪声远大于 LED 差异（绿灯 255 反而 97.79 mA，明显是采样窗口撞上了 4G 突发）。要单独测 LED，得**先把 4G 模组断电**（`{"cmd":"v4g","state":"off"}`）再测，或大幅增加采样次数取统计量。

## 测量方法与局限

- **测的是探针 VCC 总线总电流**，MCU + 4G 模组 + LED + 传感器混在一起，**分不出单项**。
- 每档只采 6 个点、间隔 0.5s，样本太少；4G 周期性突发会让 avg 抖动很大（同一状态重复测可能差 20~30 mA）。**做结论建议 n≥30**。
- `power-read` 与 RTT/SystemView/VOFA 流**不能同时**用同一个命令口，需先停采集。
- 数值含义：`0` 是有效值；`null` 表示 ADC 预热中或读失败，**不能当 0**。

## 密集收发那一档的坑

脚本第 7 档是**单向密集下行**（6s 内每 0.4s 发一条 `{"cmd":"led","state":"off"}`，QoS 0），靠上行 ACK 验证"收"。

但实测**这 6 秒几乎没有 ACK 上行**（只有 `ready` 心跳）。原因：固件的延时 ACK 是**覆盖式**的——每来一条新指令就把 `g_ack_at = now + ACK_DELAY_MS(800ms)` 往后推。发送间隔 400ms < 800ms，待发 ACK 的截止时间被一路推后，连发期间一条都发不出去，直到风暴结束才补发最后一条。

→ 所以这一档应改名为「**下行风暴 + 模组收发**」，测的是模组连续接收/转发电流。
→ 要真正做"每发必收"的压测：把间隔拉到 >1s，或改固件把 ACK 改成 FIFO 队列（不覆盖）。

## 第二轮：心跳抑制 + 长采样（v2）

> 测试日期：2026-10-12 晚
> 脚本：`power_state_test2.py`（每档 **50 点 / 1s**，统计 min/中位/avg/max/σ，并统计采样窗口内到达的 `ready` 条数）
> 目的：第一轮只采 6 点、且与 15s 心跳/60s 探活重叠，档间差异全被突发噪声淹没。这一轮**先把周期上报关掉**，把 LED、MCU、心跳三者的电流分开。

### 怎么"关掉心跳干扰"

周期上报（15s `ready` 心跳 + 60s `+++` 探活）都由 `dtu.c` 的 static 变量 `low_power` 门控：

```c
if (!low_power) {   /* DTU_Process */
    心跳 ready（HB_PERIOD_MS = 15000）;
    探活 +++ → ssta（PROBE_PERIOD_MS = 60000）;
}
```

**不改固件、不重新烧录**，直接用 SWD 把该变量写 1：

```
mklink write-ram --port COM11 --addr 0x20000584 0x01     # low_power = 1
```

（`0x20000584` 由 `arm-none-eabi-nm -nS` 从 ELF 查出，已实测读回 `01` 生效。）

- 选它而不是 `{"cmd":"sleep"}`：`low_power` **只停 DTU 说话，不影响 MCU 全速运行、不影响 LED**，是干净的"无周期发射"基线。
- **坑**：任何被识别的 MQTT 指令都会在 `main.c` 里执行 `g_low_power = 0; DTU_SetLowPower(0)` 把它清掉。所以每档流程必须是「发指令 → 等 ACK → 再写 `low_power = 1` → 开始采样」。
- 它写的是 MCU 侧标志，**没有**下发模组的 `lp` 私有指令，所以模组自身的功耗模式未变——测出的差值纯属"MCU 停掉周期发言"带来的。

### 关键结论（v2）

1. **心跳 + 探活 ≈ +30 mA（中位 65.25 vs 35.07）**，且**完全可复现**：两档"心跳开"（第 1、10 档，中位 65.25 / 64.82）与两档"心跳关"（第 2、7 档，35.07 / 35.32）几乎重合，说明这两个数就是真实基线，不再是随机噪声。
   - 每条 `ready` 只有 ~40 字节，但 4G 模组每次上行都要唤醒射频、并可能触发 RRC 状态迁移，所以 15s 一次的代价摊到平均上就有 ~30 mA，探活的模式切换更贵。
2. **噪声减半**：σ 从 34.50 → 18.09（心跳关）。残余 σ 来自模组自身的 MQTT keepalive / 网络注册等 MCU 管不了的发射。这也说明——**只要模组供电，就压不到"干净"**。
3. **LED 单项终于分离出来了**（以心跳关的两档全灭为基线 35.2 mA 中位，取中位数差值）：

   | LED | 净增电流 |
   |---|---|
   | 绿灯 255 | **+18.6 mA** |
   | 红灯 255 | +7.5 mA |
   | 黄灯 255 | +7.1 mA |
   | 红灯 64（25%） | +1.3 mA |

   绿灯明显最费电（这类高亮绿光 LED 正向压降高、同亮度电流大）；红灯与黄灯相近（约 7 mA）；调暗到 25% 时几乎不耗（+1.3 mA）。**这些差值都远大于残余噪声，可信。**
4. **睡眠态 ≈ 心跳关的运行态**（avg 41.62 vs 41.65，σ 19.82 vs 18.09）。即：`{"cmd":"sleep"}` 省下来的**几乎全部就是"心跳/探活"那一份**；MCU 进 WFI 本身在这块板上**省不出可测量的整板电流**（内核 + SysTick 那点占比太小）。
5. **第 8 档"密集收发"是全场上行最密的一档**（更正一个说法：心跳并不是"收发"之外的东西）。
   **心跳本身就是一次上行，和 ACK 在物理上没有任何区别**——都是模组射频发一包 MQTT，只是内容固定为 `{"cmd":"ready",...}`。所以决定平均电流的**不是"这包是心跳还是 ACK"，而是上行速率**（以及每次上行后射频保持高功耗状态多久）。
   - 第 8 档窗口内：`ready = 8` + ACK `其他 = 25`，合计 **33 条上行 / 114s ≈ 1 条 / 3.5s**；第 1 档是 11 条 / 95s ≈ 1 条 / 8.6s。**第 8 档发得最勤，所以 77.70 mA 最高**——这和"心跳漏没漏"无关。
   - 之所以把"心跳泄漏"单独标出来，只是因为它**意外混入**（每轮 `publish` 会清掉 `low_power`，补写回来前心跳已漏出），使这一档无法干净归因于"纯指令流量"。
   - **这一点已在第三轮拆开**：+30 mA **全部来自 15s 心跳**，探活对典型电平的贡献 ≈ 0。详见下方「第三轮」。

### 方法局限（v2 仍然存在）

- 仍是**探针 VCC 总线总电流**（MCU + 模组 + LED + 传感器），分不出单项；只有"心跳开/关"和"LED 各色"是**对照**出来的差分值。
- 残余 σ 仍有 ~20 mA，所以**只有 ≥7 mA 且跨档一致的差值**才可信（绿灯、红灯 255、黄灯 255 满足；红灯 64 与基线之差仅 1.3 mA，属于边界，仅供趋势参考）。
- CLI `power-read` 每次调用间隔 ~1s（含进程启动），时间分辨率比模组突发粗，`max` 只是"撞上突发"的指示，不具统计意义。

## 第三轮：把 +30 mA 拆开 —— 心跳 vs 探活（2×2 对照）

> 测试日期：2026-10-12 20:30 前后
> 脚本：`power_hb_probe_split.py`
> 目的：v2 里"心跳"和"探活"是**一起开关**的（都在 `if (!low_power)` 里），分不清那 +30 mA 归谁。这一轮把两者**独立开关**，做 4 档对照。

### 手法：用 `uwTick` 精确压住其中一个

`DTU_Process(now)` 里 `now == HAL_GetTick() == uwTick`（`0x2000011c`），于是：

| 想压谁 | 做法 | 地址 |
|---|---|---|
| 心跳 | 周期性把 `hb_tick` 写成**当前 uwTick**（保持 `now-hb_tick < 15s`） | `0x20000578` |
| 探活 | 周期性把 `probe_tick` 写成**当前 uwTick**（保持 `now-probe_tick < 60s`） | `0x2000057c` |
| 两个都压 | 直接写 `low_power = 1` | `0x20000584` |

均**不改固件、不烧录、不影响 MCU 运行与 LED**（LED 全程全灭）。关键点：**不能把 tick 写成未来值** —— `(uint32_t)(now - tick)` 会下溢成大数，条件立刻成立、反而马上触发。

> 用 `uwTick` 而不是 `hb_tick` 当"现在"的原因：`hb_tick` 只在心跳/探活时刷新，最坏可能落后 15s，用它做基准会压不死心跳。

### 结果（4 档，LED 全灭）

| 条件 | 中位 | avg | σ | max | 窗口内 ready | 探活痕迹(`+++`/`AT+ENTM`) |
|---|---|---|---|---|---|---|
| 1 心跳 **ON** · 探活 **ON**（对照） | **65.31** | 64.70 | 23.36 | 146.25 | 10 | 4 |
| 2 心跳 **ON** · 探活 **OFF** | **65.30** | 66.09 | 28.57 | 144.91 | 7 | **0** |
| 3 心跳 **OFF** · 探活 **ON** | **35.20** | 50.31 | 28.11 | 145.92 | 5 | **8** |
| 4 心跳 **OFF** · 探活 **OFF** | **34.97** | 39.29 | **10.93** | **65.80** | 1 | 0 |

（单位 mA；`U ≈ 3.37 V`。第 3 档 `ready=5` 基本就是探活次数——每次探活收尾会补发一条 `ready`。）

### 结论（第三轮）

1. **+30 mA 全部来自 15s 心跳，不是探活。**
   - 心跳 ON→OFF（探活都开）：中位 **65.31 → 35.20**（**−30.1 mA**）
   - 探活 ON→OFF（心跳都开）：中位 **65.31 → 65.30**（**−0.01 mA**，等于没变）
2. **探活不改"典型电平"，只制造短促突发。** 心跳关时才看得清：中位 35.20 vs 34.97（几乎相同），但 **avg 50.31 vs 39.29（+11 mA）**、**σ 28.11 vs 10.93**、**max 145.92 vs 65.80**。→ 探活每 60s 触发一次持续十几秒的高功耗窗口（切出透传 → 查询 → 恢复，模组要重建链路），把平均值抬高，但中位数不受影响。
3. **两者不叠加。** 心跳开着时，探活的边际成本 ≈ 0（射频本来就被心跳维持在高位，增量被吸收了）——这也是第 1、2 档 avg 只差 1.4 mA（噪声级）的原因。
4. **机制**：心跳是**真正的空口上行**（每 15s 一包 MQTT，模组要唤醒射频并可能触发 RRC 状态迁移），所以摊到平均上就是 ~30 mA；探活主要是**串口级交互**（`+++`、`config,get,ssta` 是模组本地状态查询，不走空口），只在收尾补发一次 `ready` —— 单次便宜，但会切模式、代价集中在一次较长的重构期。
5. 顺带看清了一件事：**那 ~145 mA 的尖峰就是上行突发**。第 4 档（什么都不发）max 只有 65.80、σ 只有 10.93，是全场最干净的基线。

**工程含义**：想降这块板的平均功耗，动**心跳周期**（`HB_PERIOD_MS`）最有效，动探活几乎没用；探活的价值是**链路自愈**，不是省电。

## 第四轮：4G 模组断电（`v4g off`）+ LED 电流分离

**已完成**（2026-10-12）。数据源 `power_v4g_off.log`、`power_led_off.log`；图表版报告见 `power-v4g-off-report.html`。

### ⚠️ 前提：`{"cmd":"v4g","state":"off"}` 不带 ICCID 会被丢弃

`main.c` 的指令校验里只有 `{"cmd":"led"}` 和 `{"cmd":"sleep"}` 豁免 ICCID 校验，`v4g` 属普通指令，
payload 里必须出现 ICCID 才 `match=1`。实测（读 `GPIOA->ODR` bit3 确认 PA3）：

| payload | PA3 | 结果 |
|---|---|---|
| `{"cmd":"v4g","state":"off"}` | 1 | 被丢弃，模组仍供电 |
| `{"cmd":"v4g","state":"off","id":"898608961026C0241530"}` | 0 | 生效，断电 |

（建议把 `v4g` 也加进 `is_sys_cmd` 豁免，和 `sleep` 一样，见 "待办"。）

### 结果：MCU 进 WFI 几乎不省电

| 状态（4G 断电，LED 全灭） | 中位 | avg | σ |
|---|---|---|---|
| MCU 运行（每圈 `__WFI()` + 1ms SysTick） | 21.70 | 21.86 | 1.25 |
| MCU 深度空闲（`g_low_power=1`，SysTick 挂起） | 21.54 | 21.49 | 0.95 |

差 **0.16 mA**。主循环本来就每圈 `__WFI()`，动态功耗已很低；21.5 mA 的主体是外设时钟 / 传感器 / 板载电路。

### 手法（不改固件、不烧录）

| 动作 | 做法 |
|---|---|
| 4G 断电 | MQTT 真发带 ICCID 的 `v4g off`，再 SWD 读 `GPIOA->ODR` bit3 确认 |
| 4G 恢复 | **只能 SWD**：写 `0x40010810` = `0x08`（BSRR 置位 PA3）。模组断电后 MQTT 收不到命令 |
| LED 切换 | SWD 直写 `TIM3->CCRx`（红 `0x40000434` / 黄 `0x40000438` / 绿 `0x4000043C`），写后读回校验 |
| 冻结周期上报 | SWD 写 `dtu.c` 的 `low_power`（`0x20000584`）= 1 |
| MCU 深度空闲 | SWD 写 `main.c` 的 `g_low_power`（`0x2000033D`）= 1 |

### 两个必须记住的 SWD 写入坑

1. **残留串口 HIL 锁会让所有写操作静默失败。**
   `write-ram` 报 `Runtime HTTP 500: HIL lock 'transport_usb-serial_COM11' held by pid=...`，
   而 `read-ram` 依旧正常 → 读数看着没问题、写入全落空（第一版测试里 4 个 LED 档电流完全一样就是这个原因）。
   处置：`mklink resources release-all`（清掉 `alive=False` 的陈旧锁），之后写入立即恢复。
2. **`write-ram` 多字节写入会因内部回读校验不一致而整体失效。**
   写 `0xFF 0x00`（2 字节）→ `Write completed but verification differed`，读回仍是 `0000`；
   改 1 字节 `0xFF` → `status ok / verified true`，读回 `ff00` = 255 ✓。
   → **一律逐字节写**。已验 1 字节写入：0x40→4000、0xC8→c800、0x01→0100、0xFF→ff00。
