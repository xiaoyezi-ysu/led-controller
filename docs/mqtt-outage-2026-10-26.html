MQTT 断流 11 小时 37 分：一场「板子失联」的复盘

2026-10-26 · 车牌 ver2 · 银尔达 YED_DTU4 @ broker.emqx.io · 证据来自 mqtt_watch 旁听日志、INA228 电流指纹、串口端口实测与蜂窝网模组对照实验

0. 一句话结论

静默时长
11 h 37 min　03:15:03 → 14:52

4 个 MQTT 端口　1883/8883/8083/8084

没有任何硬件或固件故障。板子从凌晨到下午一直在按周期正常上报，只是「电脑这一端的网络」收不到 broker 的推送。封的是端口，不是 IP，也不是 emqx 服务本身。

1. 时间线：从「以为板子死了」到「其实是端口被封」

封锁是「全封 → 全通」的二值切换：03:15 一刀切掉，14:52 一刀切回；恢复后连接延迟立刻回到 0.2 s（正常国际链路水平），中间不是高延迟或部分丢包。

2. 现象：看起来像板子坏了

  • 旁听程序 mqtt_watch 的心跳行显示 「已收 823 条，最后一条 N 秒前」，N 一路涨到 25000+，计数一动不动；
  • 线程状态一直是 alive，进程没死、日志还在写；
  • 手机用 4G 打开 GitHub Pages 上的灯控页（wss://broker.emqx.io:8084/mqtt）也连不上；
  • 板子当天凌晨起一直待在室内，固件没改过，流量余量 5.7 / 30 MB 充足。
误判陷阱：「线程 alive + 计数不动」极容易被读成「板子不发消息了」。实际上这两个量都与 broker 连接无关——alive 只说明 Python 线程还在跑，计数只在真正收到消息时才 +1。观测端一旦断链，它就会安静地聋下去，任何一侧的活动都体现不出来。

5. 到底是谁封的？两个候选机制

候选支持证据不符之处
① 链路/运营商端口级过滤
动态生效、动态解除		 只封 MQTT 端口、443 白名单放行；蜂窝物联网卡不受影响，消费级 SIM/家宽同样中招 缺少运营商侧证据，无法直接证实
② emqx 公共 broker 的反滥用拉黑
按源 IP 临时封禁		 公共 broker 被滥用严重，通常只封 MQTT 端口、放行 443；封禁时长（十余小时）与临时封禁常见量级吻合 同一出口经代理仍不通（代理出口是机房 IP，理论上不该与家宽同罪）
诚实的结论：从客户端侧无法把两者区分开——两种机制的症状完全一致（只封 MQTT 端口、二值切换、十余小时）。但「443 通 / MQTT 端口死」这个组合足以排除「IP 被封」「emqx 挂了」「DNS 或证书问题」。

5.1 一个可能的自触发因素

旁听脚本用的是 paho 的 reconnect_delay_set(min_delay=1, max_delay=30)：连接失败时从 1 s 起翻倍、封顶 30 s，也就是每 30 秒硬撞一次。11 小时 37 分 ≈ 1300 次连接尝试，全部来自同一个 IP。公共 broker 的滥用防护很容易被这种模式触发——封锁解除后它立刻重连成功，也符合「临时封禁到期」的表现。

建议：把 max_delay 提到 300 s（5 分钟一封顶），失败时温和退避；恢复后仍能自动接回，但不会把 IP 撞进黑名单。

7. 复现命令

# 1) 端口 + TLS 探测（判「IP 可达 / 端口被封」）
python - <<'PY'
import socket, ssl
for p in (1883, 8883, 8083, 8084, 443):
    s = socket.socket(); s.settimeout(6)
    try:
        s.connect(("broker.emqx.io", p)); print(p, "TCP OK")
        if p in (443, 8084):
            ctx = ssl.create_default_context(); ctx.check_hostname=False; ctx.verify_mode=ssl.CERT_NONE
            ctx.wrap_socket(s, server_hostname="broker.emqx.io"); print(p, "TLS OK")
    except Exception as e:
        print(p, "FAIL", type(e).__name__)
    finally: s.close()
PY
