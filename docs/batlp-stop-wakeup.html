一句话结论：低压保护逻辑本身一次写对，但第一次上机就「睡下去再也醒不来」。根因不在业务代码，而在 RTC 从 Stop 唤醒瞬间 RSF=0（APB1 与 RTC 核心未同步）——此时写 RTC->CRH 的 ALRIE 位会被硬件静默丢弃，下一发闹钟不再产生中断，板子便永久锁死在 Stop。修复 = 所有 RTC 寄存器访问前先等 RSF=1，并在唤醒路径上把中断门禁重开一次。

二、状态机：Stop 进出的完整闭环

三、症状：睡下去，再也醒不来

烧录后第一次实测，进睡条件满足得干干净净 —— 但睡眠之后板子像死了一样。用 OpenOCD 连上去读一组变量，得到三个互相矛盾的事实：

观测量反复读到的值说明
g_rtc_alarm_hit恒 0闹钟中断一次都没触发过
g_wdg_kick恒 12看门狗喂狗计数不增长 ⇒ 主循环没在跑
uwTick冻结SysTick 停 ⇒ 确实处于 Stop
RTC CNT持续增长RTC 照走 ⇒ 时钟源没问题（LSE/LSI 都活着）
矛盾点：RTC 明明在走，闹钟也挂上了（ALR 值正确），可中断就是不发；中断不发 ⇒ 主循环永远停在 WFI ⇒ uwTick 冻结、喂狗停摆 ⇒ 死锁。这不是"睡太深"，是"醒不来"。

排查中先后排除了：时钟配置（CNT 在涨）、闹钟值（ALR 回读正确）、EXTI 线（IMR 已开）、NVIC 总开关。每一步都把嫌疑指向同一个地方 —— 中断使能位 RTC->CRH.ALRIE 到底有没有真的写进去。

四、根因：RSF=0 时写 CRH 被硬件丢弃

RM0008（STM32F1 参考手册）RTC 章节对 CRL.RSF（Registers Synchronized Flag）有明确约束：

APB1 接口与 RTC 核心是两个完全独立的时钟域。RTC 核心在内核复位、睡眠、Stop 期间照常运行，而 APB1 总线接口会停摆。RSF=1 表示 APB1 已与 RTC 核心重新同步。当 RSF=0 时：读 RTC 寄存器的值不可信，写 CRH/CRL 也无效。

从 Stop 唤醒的最初一小段时间里，APB1 刚刚上电、还没来得及和 RTC 核心同步，此刻 RSF=0。而我们的唤醒路径一进主循环就调用 RTC_APP_ArmIn() 重挂闹钟，其中包含 RTC->CRH |= RTC_CRH_ALRIE —— 这一位被硬件静默丢弃了（不报错、不回读异常，就是没写进去）。于是：

  1. 本轮的闹钟中断服务已执行完（ALRIE 被硬件在中断入口自动清掉）；
  2. 唤醒路径试图重开 ALRIE，因 RSF=0 失败；
  3. 下一发闹钟到点，中断不产生 ⇒ 没有 g_rtc_alarm_hit ⇒ 主循环没被告知要醒；
  4. WFI 立刻再次进 Stop —— 永久锁死。
为什么第一轮能进睡？初始化阶段（RTC_APP_Init）跑在完整上电、时钟早已稳定的环境里，RSF=1，ALRIE 写得进去，所以第一次挂闹钟是成功的。问题只出在"从 Stop 醒来再写"这条路径上 —— 这也解释了为什么它看起来像个偶发问题，实则必然发生。

五、修复：三处加固

① 统一入口 rtc_wait_rsf() —— 所有 RTC 操作前先等同步

static void rtc_wait_rsf(void)
{
  uint32_t guard = 0;
  while (!(RTC->CRL & RTC_CRL_RSF))
    if (++guard > 2000000u) break;   /* ≈250ms @8MHz，防呆 */
}

所有碰 RTC 寄存器的地方（Init / ArmIn / WakeArmed / RearmIRQ / 看门狗快照）都先调它。带 guard 计数是为了万一硬件异常也不至于卡死在 while。

② 新增 RTC_APP_RearmIRQ() —— 唤醒路径第一件事

uint8_t RTC_APP_RearmIRQ(void)
{
  if (!s_rtc_ok) return 1u;
  rtc_wait_rsf();                       /* ★ 先等 APB1 同步 */
  RTC->CRH |= RTC_CRH_ALRIE;            /* 必须在 CNF=0 且 RSF=1 时写 */
  EXTI->IMR |= RTC_EXTI_LINE;
  NVIC_SetPriority(RTC_Alarm_IRQn, 2);
  NVIC_EnableIRQ(RTC_Alarm_IRQn);
  s_irq_gate_ok = (uint8_t)((RTC->CRH & RTC_CRH_ALRIE) &&
                  (NVIC->ISER[1] & (1u << ((uint32_t)RTC_Alarm_IRQn - 32u))));
  return s_irq_gate_ok ? 0u : 1u;
}

在 main.c 的 if (g_rtc_alarm_hit) 分支最前面调用。这样无论上次睡眠里发生了什么，醒来第一件事就是把中断门禁重开，锁死状态无法自持。

③ WakeArmed() 加门禁校验 + ArmIn() 双重回读

RTC_APP_WakeArmed() 现在不只看"闹钟挂没挂"，还实际回读 RTC->CRH.ALRIE 和 NVIC->ISER[1] 的门禁位，两者缺一就返回 0（视为未武装）。ArmIn() 写完 ALR 后同样做第二道校验，失败则重试一次并置 s_wake_armed=0，让上层能感知异常而不是盲目进睡。

写 CRH 的关键约束（牢记）：只有 ALR/CNT/PRL 需要先 CNF=1 进配置模式；CRH/CRL 不需要 CNF，而且 CNF=1 时反而写不进去。它们只需要 RSF=1。早期的实现把 CRH 也包进了配置模式，是另一处隐患，已一并纠正。

六、两个必须记住的踩坑（自省）

坑一：RTC_CRH / CRL 的地址搞反了

排查中一度按错误的寄存器映射解读，把 0x40002800 当 CRL、0x40002804 当 CRH，导致 ALRIE/SECIE/RSF 的解读全错，多花了好几轮。

寄存器地址本次实测值解读
RTC_CRH0x400028000x0002ALRIE=1（闹钟中断使能）
RTC_CRL0x400028040x0029RSF=1（bit3）/ RTOFF=1（bit5）
RTC_PRLL0x4000280C32767预分频低 16 位
RTC_CNTH/L0x40002818/1C—秒计数（跨 Stop 唯一时标）
RTC_ALRH/L0x40002820/24—闹钟值

记忆口诀：CRH 在低地址（0x…00），和 CNT/ALR 的顺序一致（H 在前）。每个寄存器占 32 位字、只有低 16 位有效。

坑二：RTC_Alarm_IRQn = 41 落在 NVIC->ISER[1] 的 bit9

排查时只读了 NVIC->ISER[0]（0xE000E100）得到 0，便断言"闹钟中断没使能"，把方向带偏。实际上 Cortex-M 中 IRQ 32–63 位于 ISER[1]（0xE000E104），而：

  • RTC_Alarm_IRQn = 41（与 EXTI15_10=40、USBWakeUp=42 相邻，与 startup_stm32f103xb.s 中 RTC_Alarm_IRQHandler 的位置吻合）；
  • 对应 ISER[1] 的 bit(41-32)=bit9；
  • 实测 NVIC->ISER[1] = 0x2A0，bit9 = 1 ⇒ 中断其实一直是使能的。
教训：基于这个错误判断曾做了一处 RTC_APP_EnableAlarmIRQ() 修改，事后已撤销还原。真相是中断门禁没问题，问题在 RSF=0 时写 CRH 被丢弃 —— 二者表象相似（都是"ALRIE 没生效"），但根因完全不同。

另外提醒：RTC_IRQn=3 是秒中断，和闹钟中断是两个不同的 IRQ，别混用。

坑三：Stop 态读外设寄存器会「整片返 0」，别当故障

进程 Stop 后，AHB/APB 外设时钟被停，用 SWD 读 RTC_CRL/RTC_CRH、EXTI->IMR、NVIC->ISER 会得到 0 —— 这看起来像"寄存器被清零了/系统崩了"，其实只是总线停摆。只有 RTC 备份域部分还能读。

正确判法：判断板子是否在 Stop，看 RCC_CR 与 uwTick 是否冻结，或者 halt 后再重读一次寄存器。切勿据 Stop 态的单次读数下结论。

九、Q & A

Q1：为什么"进睡"没问题，"醒来"才出问题？
进睡路径在正常运行的上下文中执行，时钟早已稳定、RSF=1，写 ALRIE 成功。真正第一次写 ALRIE 是在 RTC_APP_Init()（完整上电后），也成功。只有"从 Stop 唤醒后立刻重写"这一条路径会遇到 RSF=0 的窗口。所以问题必然发生，却只在睡眠之后暴露。
Q2：为什么不干脆在唤醒后加个固定延时，等 RSF 自己变 1？
可以，但不严谨。RSF 的出现时机与 APB1 上电、分频配置有关，固定延时要么不够（仍丢写）、要么过长（浪费电流预算）。轮询 RSF 位是 RM0008 推荐的正确做法，也把"到底等多久"交给硬件自己说了算，还带 guard 防卡死。
Q3：低压保护会跟 lp_cycle（2h 自动低功耗）打架吗？
不会。main.c 里在线检测块的门禁是 if (s_batlp_en && !g_lp_cycle && !s_bat_sleep) —— 处于 lp_cycle 流程中时不再叠加低压检测；而 s_bat_sleep 会并入 want_stop，两者共用同一套 Stop 退出、时钟恢复逻辑。恢复路径里 SystemClock_Config() 依然是必须的（Stop 退出后 SYSCLK 回落 HSI，不重配则 UART 波特率全错）。
Q4：这个 bug 会不会在别的 Stop 唤醒场景里也埋着？
会 —— 凡是在"从 Stop 醒来"的路径上直接写 RTC->CRH/CRL 的代码都有同样风险。本次把等待同步收敛到统一的 rtc_wait_rsf()，并让 wakeup 一定先走 RTC_APP_RearmIRQ()，等于在所有可能路径上打了同一道补丁。后续新增 RTC 相关代码，只要坚持"先 rtc_wait_rsf() 再读写"，就不会重犯。
