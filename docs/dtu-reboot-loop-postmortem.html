0. 先直接回答你的问题

「主要问题是状态机跳转的时机不对？」—— 对，这是核心。但它是两根绞在一起的绳子，缺一根都解释不通。

把 5 小时的怪象拆开，其实只有两件事在起作用：

  1. 探活状态机用「固定时间窗口」去赌一个「延迟浮动 1~4 秒」的应答 —— 窗口 / 清行时机与应答到达时刻错位，就把真实应答丢掉 → 误判离线 → 重启 DTU → 引发连锁（回声、乱码、电流掉到几 mA）。这是真实存在的 bug。
  2. 修好的代码根本没被烧进芯片 —— 构建系统的一个小错误让 .hex 停留在 4 小时前，OpenOCD 烧的是旧固件还报 “Verify OK”。所以「改了没效果」不是改错了，是没生效。
一句话因果链：应答迟到 → 被状态机吃掉 → 判死重启 DTU → DTU 重启期 TX 悬空 → MCU 收到自己的「回声+乱码」 → 再次误判 → 无限循环；而旧 hex 让这个循环一直没被修复版代码救回来，于是看起来像「接线坏了」。

1. 你看到的三个现象（同一件事的三个面）

现象你的观察当时的误判
电流掉到几 mA 「4G 模组没上电啊，所以没测到」 一度以为固件把 V4G 切了。查实：自愈流程从不切 V4G，全工程唯一的 V4G_Set(0) 在 lp_cycle 收尾；那是历史残留值，你看到的是模组被反复重启的抖动。

状态机来回跳 POLL → RECOVER → WAIT_BOOT 循环不停 这个是真的 —— 就是真凶 #1 的表现。

2. 恶性循环全景图

循环的关键放大器：DTU 重启要 30~60 秒才能注网完毕，而固件在这段时间里又去探活——必然失败，于是再发一条 save。DTU 永远拿不到一段完整的启动时间，从此再也回不到在线状态。「模组启动慢」（官方正常行为）+「探活窗口太紧」（固件问题）相撞，就是这个死循环的引擎。

3. 真凶 #1：状态机跳转的时机（核心 bug）

旧实现：异步子状态机 —— 用「固定的表」去赌「浮动的钟」

探活每 60 s 触发一次，走的是三个状态接力：

状态 / 常量等待干什么
RECOVER_ESC
ESC_GUARD_MS = 1000		+++ 后等 1 s到点后 dtu_clear_line() 清缓冲，发 config,get,ssta，切下一态
RECOVER_SSTA
SSTA_TIMEOUT_MS = 5000		最多等 5 s看到整行就解析 ssta；不是 ssta 应答就 clear_line() 清掉继续等；5 s 还没等到 → 判死 → config,set,save
错在哪：「+++ 的回显」「ssta 的应答」到达时间是浮动的（模组忙时 1~4 s，疲态更久），但状态机用 1 s 守卫 + 5 s 超时 + 一个 clear_line 这三块固定积木去卡它。任何一次「应答落在 clear_line 之前、或超过 5 s 窗口」，真实应答就被丢掉 —— 而且丢一次就触发重启，重启又制造更多延迟，误差自我放大。
为什么今早能跑通？今天上午模组轻载、应答快，时序碰巧对上了；一旦链路有波动就翻车。所以这是「成功率不是 100%」的时序 bug，不是逻辑错。

4. 真凶 #2：烧进去的是 4 小时前的旧固件

这是整场迷局里最贵的一个坑，因为它把「改对了」伪装成「改了没用」。

检查项结果
build/Debug/*.elf 时间戳05:06 —— 是新的（编译确实成功了）
build/Debug/*.hex 时间戳01:39 —— 停在 3.5 小时前
芯片 Flash 里搜特征串搜到旧代码的 "escape transparent"，搜不到新代码的 "blocking" → 芯片上跑的是旧固件
OpenOCD 的反馈“Verify OK” —— 它验的是那个旧 hex，所以永远 OK
根因：ninja 构建时偶发的 .ninja_lock 占用报错，把编译链最后一步「.elf → .hex」（objcopy）吞掉了。ninja 报错只在收尾，容易让人以为「只是收尾噪音、编译其实成功了」—— 实际上 elf 成功、hex 失败，而烧录用的是 hex。
处置：手工补一步 arm-none-eabi-objcopy -O ihex xxx.elf xxx.hex 重新生成 hex → 重新烧录 → Flash 验尸确认 "blocking" 已上芯。此后再观察，状态机行为立刻与代码一致。
教训（已写进项目备忘录）：烧录前必查 .hex 的 mtime，或改用「elf 直接下载」的流程；只要 ninja 出现过 lock 报错，就当作 hex 可疑处理。

5. 修复与实机验证

修复 ①：探活改阻塞式

新增 dtu_probe_blocking()（≈4.2 s）：+++ → 等 1300 ms → 发 config,get,ssta → 死等 1500 ms → 读整行 → AT+ENTM → 等 1000 ms → 返回 ssta==4。失败时先重试一次，两连败才判死（旧逻辑是一次失败就重启）。

为什么它能行：应答窗口是自己留出来的，不存在「清行时机」和「应答到达」的竞争；而且它只在空闲时（cmd_rx_tick 守卫通过）被调用，阻塞期间主循环暂停、心跳不冲突 —— 和当天 100% 成功的 DTU_DebugProbe 是同一套节奏。

修复 ②：nettime 授时回接

新增 DTU_QueryNettime()（指令模式阻塞 1.5 s，解析 config,nettime,ok,... 后写 RTC）。此前判定它「会卡死通道」其实是同一个应答被吃掉的误判；PC 直连复测它 0.15 s 秒回。

实测结果

验证项结果

6. 两个真凶的关系（为什么缺一不可）

真凶 #1

探活时机的 bug

它制造了恶性循环：把模组启动慢误判成离线，反复重启。

没有它，就没有回声、没有电流抖动、没有状态机乱跳。

真凶 #2

旧 hex 没烧进去

它掩盖了修复：代码对了，芯片上是旧的，所以行为一直不变。

没有它，第一轮改完就该好了 —— 不至于排查 5 小时、还错怪了接线。

组合起来才形成「越修越像硬件问题」的假象：你改了固件 → 行为完全不变 → 于是怀疑硬件/接线 → 去动线 → 链路波动 → 触发更多重启 → 现象更像硬件坏了 → 循环。

7. 沉淀：5 条经验

  1. 烧录前先看 .hex 的 mtime。ninja 的 lock 报错可能吞掉 objcopy，「Verify OK」只证明「烧的和 hex 一样」，不证明「hex 是新的」。
  2. 「改了没效果」的第一反应是验证产物，而不是怀疑硬件。最省时的验尸法：在 Flash 里搜新旧代码的唯一特征字符串。
  3. 和设备通信的等待窗口不要「赌」。对方应答延迟浮动时，用「发完死等 + 读就判 + 失败重试」的阻塞式，好过「固定 guard + clear + 固定超时」的异步状态机。
  4. 自愈策略要留出「对方正在启动」的余量。一次性判死重启，会把「慢启动」变成「永久起不来」。
  5. 悬空的 TX/RX 会自导自演。「MCU 收到自己发的字节」= 对端没在驱动，是链路在对端失效的表现，不要直接推成「接线短路」。
